Visión general

El API expone 18 endpoints bajo el prefijo /api/v1. Está organizado en cinco bloques funcionales: productos, formatos, primas permitidas, procesamiento y consultas / reportes.

BloquePropósitoEndpoints clave
Productos Catálogo lógico (Bolívar, Mapfre, etc.). Cada uno tiene un id, code y opcionalmente reglas / mapeos base. /products
Formatos Variantes de archivo de un producto (planes, vigencias). Definen file_prefix, sheet_name, header_row, mapeos y reglas. /product-formats, /product-formats/active, /product-formats/match-test
Primas permitidas Lista blanca numérica de primas válidas por producto. Se usa para validar cada póliza. /products/allowed-premiums
Procesamiento Escanea SFTP / disco, encola archivos, expone progreso y permite reintentos. /process/scan, /process/progress, /files/retry
Consultas y reportes Listar archivos, descargar originales, ver pólizas, exportar reportes de validación en CSV/XLSX. /files, /policies, /policies/search, /files/summary, /files/validation-*

Flujo end-to-end

Camino feliz desde producto nuevo hasta consulta de pólizas.

1
Crear producto

POST /products con id + code.

2
Registrar formatos

POST /product-formats por cada variante.

3
Activar formato

PATCH /product-formats/active.

4
Probar matching

POST /product-formats/match-test con headers.

5
Definir primas

PUT /products/allowed-premiums.

6
Lanzar proceso

POST /process/scan (async).

7
Monitorear

GET /process/progress.

8
Listar archivos

GET /files.

9
Reportes

GET /files/summary + validation-*.

10
Consultar pólizas

GET /policies/search.

Atajo: si solo quieres ver el sistema vivo, llama POST /api/v1/bootstrap/sample-products para sembrar productos de ejemplo y saltar directo al paso 6.

2 Crear varios formatos para un producto

    
Un producto puede tener N formatos (por plan, por convenio, por aseguradora origen). Cada formato describe
    cómo leer su archivo: prefijo del nombre, hoja, fila de cabecera, mapeo de columnas y reglas de validación.


    

      

        POST
        /api/v1/product-formats
      


      

        
        
        
      

      

        
{
  "id": "bolivar_vg_plan_a",
  "product_id": "bolivar_vida_grupo",
  "name": "Plan A — Convenio empleados",
  "file_prefix": "BOL_VG_A_",
  "sheet_name": "Polizas",
  "header_row": 3,
  "priority": 10,
  "active": true,
  "mappings": [
    { "target_field": "credit_number",   "source_header": "NRO CREDITO",    "required": true },
    { "target_field": "document_number", "source_header": "DOCUMENTO",      "required": true },
    { "target_field": "premium",         "source_header": "PRIMA",          "required": true },
    { "target_field": "customer_name",   "source_header": "NOMBRE",         "required": false }
  ],
  "rules": [
    { "type": "allowed_premium", "field": "premium" },
    { "type": "non_empty",       "field": "document_number" }
  ]
}

4 Probar el matching antes de procesar

    
Simula el algoritmo de selección: dado un nombre de archivo y las cabeceras leídas, devuelve qué formato
    gana, cuántos campos requeridos calzaron y por qué un candidato fue descartado.

    

      

        POST
        /api/v1/product-formats/match-test
      

      
{
  "file_name": "BOL_VG_A_2026_06.xlsx",
  "product_id": "bolivar_vida_grupo",
  "headers": ["NRO CREDITO", "DOCUMENTO", "NOMBRE", "PRIMA", "VIGENCIA"]
}

      

        Respuesta incluye: matched, winner (formato ganador), y un arreglo candidates con
        required_total, required_matched, mapped_match_count y score.
        El de mayor score con required_ok=true gana.
      

      

        
Probar ahora

        

          
        

        
        

        

      

    

  


  
  

    
5 Establecer las primas permitidas

    
Cada producto tiene una lista blanca de primas válidas. Cualquier póliza con una prima fuera de esta lista
    queda marcada como inválida durante el procesamiento.


    

      
Reemplazar la lista completa (idempotente)

        /api/v1/products/allowed-premiums

6 Procesar los archivos

    
Dispara el escaneo del origen (SFTP / disco) y encola cada archivo nuevo a los workers.
    El POST regresa inmediatamente; el trabajo continúa en segundo plano.

    

      

        POST
        /api/v1/process/scan
      

      
HTTP/1.1 202 Accepted
{
  "status": "queued",
  "enqueued": 7,
  "message": "archivos escaneados y encolados para procesamiento asíncrono con workers"
}

      

        
Probar ahora

Códigos de error frecuentes

    

      

        
HTTPCuándo apareceCómo resolver

        

          400
          Campos obligatorios vacíos (id, code, product_id, file_id, etc.) o JSON inválido.
          Revisar el body. Si el error incluye missing_fields, completar esos campos del producto / formato.
        

        

          404
          file_id inexistente, o archivo archivado faltante en disco.
          Confirmar el ID con GET /files. Si el binario fue purgado, no es recuperable vía API.
        

        

          405
          Método HTTP no permitido en la ruta.
          Verificar la tabla de referencia: cada ruta acepta solo los métodos listados.
        

        

          500
          Falla persistiendo en almacén (DB / FS).
          Revisar logs del API; usualmente indica problema de conexión o permisos.
        

        

          502
          /process/scan no pudo contactar el origen (SFTP / disco).
          Verificar credenciales y conectividad de origen; revisar variables de entorno.
